# Протоколы собраний

Веб-приложение для ведения протоколов собраний: планирование повестки, фиксация задач и дедлайнов,
ИИ-суммаризация обсуждений и аудиозаписей с выделением решений.

Проект учебный (курс «Fullstack», 1 семестр), разрабатывался поэтапно. Выполнены все пять лабораторных работ,
итог — работающее fullstack-приложение (MVP):

| ЛР | Содержание |
|---|---|
| №1 | интерфейс и каркас frontend |
| №2 | backend на FastAPI, PostgreSQL, SQLAlchemy, CRUD |
| №3 | архитектура frontend (FSD), формы, валидация, анимации |
| №4 | аутентификация и авторизация (JWT access + refresh токены) |
| №5 | интеграция: все экраны работают с реальными данными, собрания и задачи создаются, редактируются и удаляются через интерфейс |

## Быстрый старт
Нужны Docker (запущенный), Python 3.11+ и Node.js 18+. Из корня репозитория:

```bash
bash scripts/lab5-check.sh --quick      # поднять БД, backend и frontend (порядка 10 секунд после первой установки)
```

Откройте http://localhost:5173 и зарегистрируйтесь. Swagger: http://localhost:8000/docs.
Скрипт напечатает команду `kill` для остановки; если она потеряна: `pkill -f "uvicorn app.main"; pkill -f vite`.

Полная проверка (тесты, сквозной сценарий через API, сборка) — `bash scripts/lab5-check.sh`;
подробности и ручной запуск в трёх терминалах описаны ниже.

## Пользовательские сценарии
1. Зарегистрироваться и войти; выйти из приложения.
2. Посмотреть список своих собраний и открыть протокол.
3. Создать собрание: название, дата, повестка, аудиозапись.
4. Прочитать резюме и решения по собранию, при необходимости поправить их вручную.
5. Изменить повестку или удалить собрание.
6. Отследить задачи, ответственных и дедлайны; добавить, изменить, удалить задачу, сменить её статус.

## Экраны
| Экран | Маршрут |
|---|---|
| Вход | `/login` (публичный) |
| Регистрация | `/register` (публичный) |

## Запуск вручную

### 1. Настройки окружения
```bash
cp backend/.env.example backend/.env
```
Откройте `backend/.env` и задайте значения (файл не попадает в Git):

| Переменная | Назначение |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | придумайте сами; Docker создаст БД с этими данными, backend подключится с ними же |
| `POSTGRES_HOST`, `POSTGRES_PORT` | `localhost`, `5432` (если порт занят, поставьте другой, например `5433`) |
| `CORS_ORIGINS` | адреса frontend через запятую (по умолчанию `http://localhost:5173`) |
| `JWT_SECRET_KEY` | обязателен, не короче 32 символов: `python -c "import secrets; print(secrets.token_hex(32))"` |
| `ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_DAYS` | сроки токенов (15 минут и 7 дней) |

Frontend обращается к API по `http://localhost:8000`; другой адрес задаётся переменной `VITE_API_URL`
(скопируйте корневой `.env.example` в `.env`).

### 2. База данных (из корня репозитория)
```bash
docker compose --env-file backend/.env up -d db
```
Без Docker создайте БД и пользователя в своём PostgreSQL и впишите их в `backend/.env`.

### 3. Backend (из каталога `backend`)
```bash
cd backend
python -m venv .venv
source .venv/bin/activate                  # Windows (cmd/PowerShell): .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```
- Таблицы создаются автоматически при старте (`Base.metadata.create_all`); существующие таблицы не изменяются.
  Если БД создавалась до ЛР №4 (нет таблиц `users`, `refresh_tokens`, колонки `meetings.owner_id`),
  пересоздайте её: `docker compose --env-file backend/.env down -v`, затем снова `up -d db`.
- `uvicorn` запускайте из каталога `backend`: именно там ищется файл `.env`.

### 4. Frontend (из корня репозитория)
```bash
npm install
npm run dev      # http://localhost:5173
```

### Остановка
```bash
docker compose --env-file backend/.env stop db       # остановить БД, данные сохраняются
docker compose --env-file backend/.env down -v       # удалить БД вместе с данными
```
Backend и frontend останавливаются через Ctrl+C в своих терминалах.

### Частые проблемы
- **`port is already allocated` (5432):** порт занят другим контейнером или PostgreSQL на компьютере.
  Найдите: `docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'`, остановите лишнее (`docker stop <имя>`)
  или смените `POSTGRES_PORT` в `backend/.env`.
- **Docker не отвечает:** запустите Docker Desktop и дождитесь состояния «Engine running».
- **В приложении «Не удалось связаться с сервером»:** не запущен backend или БД.

## Модель данных
Основная сущность — собрание (`meetings`). Повестка, решения и задачи относятся к одному собранию
(связь «один ко многим»). Собрание принадлежит пользователю (`owner_id`); задачи, повестка и решения
наследуют владельца через собрание.

| Таблица | Поля |
|---|---|
| `users` | `id` (PK), `email` (уникальный), `name`, `password_hash`, `created_at` |
| `refresh_tokens` | `id` (PK), `user_id` (FK → users.id), `token_hash` (уникальный), `created_at`, `expires_at`, `revoked_at` |
| `meetings` | `id` (PK), `owner_id` (FK → users.id), `title`, `date`, `summary`, `audio_path` |
| `agenda_items` | `id` (PK), `meeting_id` (FK → meetings.id), `position`, `text` |
| `decisions` | `id` (PK), `meeting_id` (FK → meetings.id), `text` |
| `tasks` | `id` (PK), `meeting_id` (FK → meetings.id), `title`, `assignee`, `deadline`, `status` |

- Внешние ключи объявлены с `ON DELETE CASCADE`, а в SQLAlchemy у связей стоит `cascade="all, delete-orphan"`:
  при удалении собрания удаляются его повестка, решения и задачи.
- `tasks.status`: `in_progress` («В работе»), `done` («Готово»), `postponed` («Отложена»); во frontend те же значения.
- В API повестка и решения передаются списками строк, разбиение на строки таблиц делает backend.

## API
| Метод | Адрес | Описание | Успех |
|---|---|---|---|
| POST | `/auth/register` | регистрация (`email`, `name`, `password`) | 201 |
| POST | `/auth/login` | вход: форма `username` (email) + `password`; выдаёт access и refresh токены | 200 |
| POST | `/auth/refresh` | новая пара токенов по refresh token (использованный отзывается) | 200 |
| POST | `/auth/logout` | отозвать refresh token текущей сессии | 204 |
| GET | `/auth/me` | текущий пользователь \* | 200 |
| GET | `/meetings` | список собраний текущего пользователя (`skip`, `limit`) \* | 200 |
| POST | `/meetings` | создать собрание с повесткой и решениями \* | 201 |
| GET | `/meetings/{id}` | собрание с повесткой, решениями и задачами \* | 200 |
| PATCH | `/meetings/{id}` | изменить поля; переданные `agenda`/`decisions` заменяют список целиком \* | 200 |
| DELETE | `/meetings/{id}` | удалить собрание со связанными записями \* | 204 |
| GET | `/tasks` | список задач (фильтры `meeting_id`, `status`) \* | 200 |
| POST | `/tasks` | создать задачу (`meeting_id` в теле) \* | 201 |
| GET | `/tasks/{id}` | одна задача \* | 200 |
| PATCH | `/tasks/{id}` | изменить поля задачи \* | 200 |
| DELETE | `/tasks/{id}` | удалить задачу \* | 204 |
| GET | `/health` | проверка работы сервиса | 200 |

\* — приватный маршрут: нужен заголовок `Authorization: Bearer <access token>`.

Ошибки:
- `401` — нет токена, токен некорректен или истёк, неверный email/пароль, refresh token недействителен;
- `403` — собрание или задача принадлежит другому пользователю;
- `404` с понятным текстом (`{"detail": "Собрание с id=9999 не найдено"}`), в том числе при создании задачи
  для несуществующего собрания;
- `409` — email уже зарегистрирован;
- `422` при некорректных данных: пустое название, неверная дата или статус, нечисловой id,
  явный `null` в обязательных полях при PATCH.

## Аутентификация и авторизация

### Как это работает
1. **Регистрация** `POST /auth/register`: email (приводится к нижнему регистру, уникален), имя, пароль 8–128 символов.
   Пароль хранится только как хеш **argon2id** (`argon2-cffi`) — алгоритм, предназначенный для паролей:
   с солью и настраиваемой стоимостью. Ответ не содержит пароль или хеш.
2. **Вход** `POST /auth/login` (форма OAuth2: `username` = email, `password`) выдаёт два токена:
   - **access token** — JWT (HS256, подпись `JWT_SECRET_KEY`), claims `sub`, `type=access`, `iat`, `exp`;
     срок `ACCESS_TOKEN_EXPIRE_MINUTES` (15 минут);
   - **refresh token** — случайная строка (`secrets.token_urlsafe(48)`); срок `REFRESH_TOKEN_EXPIRE_DAYS` (7 дней).
     В БД лежит только его SHA-256, поэтому утечка таблицы не даёт рабочих токенов. Токен — запись в таблице
     `refresh_tokens`, а значит, его можно отозвать (одна запись = одна сессия).
3. **Обновление** `POST /auth/refresh`: по действующему refresh token выдаётся новая пара, использованный токен
   отзывается (ротация). Ответ `401`, если токен неизвестен, истёк, отозван или вместо него передан access token.
4. **Текущий пользователь** `GET /auth/me`. Защита маршрутов — зависимость `get_current_user`: проверяет подпись,
   срок, тип токена и существование пользователя. Публичны только `/health` и `/auth/register|login|refresh|logout`.
5. **Выход** `POST /auth/logout`: отзывает refresh token текущей сессии. Другие сессии пользователя продолжают
   работать. Запрос идемпотентен.

### Права доступа
Данные принадлежат пользователю: собрание хранит `owner_id`, задачи проверяются по владельцу своего собрания.
Списки содержат только записи текущего пользователя. Чтение, изменение и удаление чужой записи дают `403`,
несуществующей — `404`. Создать задачу в чужом собрании нельзя.

### На стороне frontend
- `shared/api/http.ts` добавляет `Authorization: Bearer …` к приватным запросам. При `401` он один раз обновляет
  токены и повторяет запрос; параллельные запросы ждут одно общее обновление (refresh token одноразовый).
  Если обновить не удалось, токены очищаются, пользователь попадает на `/login` с сообщением «Сессия истекла».
- Access token хранится в памяти, refresh token — в `localStorage`. После перезагрузки страницы сессия
  восстанавливается по refresh token. Выход в одной вкладке завершает сессию и в остальных.
- `RequireAuth` закрывает приватные маршруты, `GuestOnly` не пускает вошедшего на `/login` и `/register`.
- «Выйти» отзывает refresh token на сервере и очищает состояние на клиенте (даже если сервер недоступен).

### Ограничения
- `localStorage` доступен скриптам страницы (уязвимость при XSS); в production refresh token лучше хранить в `httpOnly`-cookie.
- Access token без состояния: после выхода он действует до истечения срока (до 15 минут); отзывается только refresh token.
- Нет ограничения числа попыток входа и подтверждения email.

## Архитектура frontend
Код разделён по упрощённой схеме Feature-Sliced Design. Слой может импортировать только слои ниже себя
(`app` → `pages` → `features` → `entities` → `shared`); импорты идут через `index.ts` среза, алиас `@/` = `src/`.

```
src/
  app/        # настройка приложения: тема MUI, маршрутизация, RequireAuth, общий каркас
  pages/      # экраны: login, register, meetings, meeting, new-meeting, tasks
  features/   # пользовательские действия
    auth-by-email/         # формы входа и регистрации + валидация
    logout/                # кнопка выхода
    create-meeting/        # форма нового собрания + валидация
    edit-meeting/          # диалог редактирования собрания (название, дата, повестка, резюме, решения)
    delete-meeting/        # удаление собрания с подтверждением
    add-task/              # форма добавления задачи
    edit-task/             # диалог редактирования задачи
    delete-task/           # удаление задачи с подтверждением
    change-task-status/    # смена статуса задачи
    filter-tasks/          # фильтр по статусу и поиск
  entities/   # сущности предметной области: типы, API, базовые компоненты
    user/                  # User, AuthProvider и useAuth (состояние сессии), userApi
    meeting/               # Meeting, MeetingCard, meetingApi, общая валидация
    task/                  # Task, TaskStatusChip, DeadlineText, taskApi, валидация
  shared/     # общее без привязки к предметной области
    api/                   # http.ts (fetch-клиент, токены, автообновление), tokenStorage.ts, ApiError
    lib/                   # useAsync, validation, date, plural
    ui/                    # AsyncBoundary, StringListEditor, ConfirmDialog, AuthCard
```

Дублирования нет: статус, дедлайн и карточка собрания реализованы один раз в `entities`, состояния экранов
с данными — один раз в `AsyncBoundary`, список строк (повестка, решения) — один раз в `StringListEditor`.
Форматы данных согласуются в `entities/*/api`: там backend-поля преобразуются в модели frontend
(`meeting_id` ↔ `meetingId`, `audio_path` ↔ `audioName`).

### Интерактивность, состояния и ошибки
- Формы: вход, регистрация, новое собрание, редактирование собрания, добавление и редактирование задачи.
  Клиентская валидация: обязательные поля, длина, корректность даты, тип и размер аудио (до 50 МБ), совпадение паролей.
  Ошибки показываются под полем после ухода из поля или при попытке сохранить; на время запроса поля блокируются.
- Экраны с данными: **загрузка** (скелетоны), **ошибка** (с кнопкой «Повторить»), **нет данных** (с призывом
  к действию), отдельно — «ничего не найдено» при фильтрации.
- После создания, изменения или удаления экран обновляется сразу, без перезагрузки: изменённая запись подставляется
  в состояние экрана, удалённая убирается, после удаления собрания открывается список. Удаление всегда с подтверждением.
- Ошибки сервера показываются понятным текстом: `422` — «Проверьте поля: Название, Дедлайн», `403` — «Нет доступа
  к этому собранию», `404` — «Собрание не найдено», сбой сети — «Не удалось связаться с сервером».
  Для `4xx` кнопка «Повторить» не показывается (повтор ничего не изменит), для сбоев сети и `5xx` — показывается.
- Анимации: плавное появление экранов и карточек, раскрытие форм и добавление/удаление пунктов списков,
  появление и скрытие строк таблицы при фильтрации, подъём карточки при наведении. Отключаются при системной
  настройке «уменьшить движение».
- Просроченные задачи выделяются красным.

## Тесты и проверка MVP

### Автотесты
```bash
cd backend && pip install -r requirements-dev.txt && pytest -v     # backend, база — SQLite в памяти
npm test                                                           # frontend: Vitest + Testing Library
npm run build                                                      # проверка типов и сборки
```
- **Backend** (50 тестов): регистрация, вход, токены, refresh, выход, права доступа (`tests/test_auth.py`);
  CRUD собраний и задач, фильтры, ошибки 404 и 422, замена повестки и решений при PATCH, каскадное удаление.
- **Frontend** (32 теста): подменяют `fetch` и проверяют экраны на «сервере в памяти» — загрузка данных, создание,
  редактирование и удаление, обновление экрана после операции, ошибки валидации (клиентской и серверной), `403`, `404`,
  сбой сервера, а также клиент API (подстановка токена, обновление по `401`, одно обновление для параллельных
  запросов, потеря сессии).
- При каждом push GitHub Actions (`.github/workflows/ci.yml`) запускает `pytest`, `npm test` и `npm run build`.

### Сквозная проверка одной командой
```bash
bash scripts/lab5-check.sh              # БД (Docker) + pytest + backend + сквозной сценарий + npm test + сборка + frontend
bash scripts/lab5-check.sh --quick      # только запуск, без тестов и сборки (для демонстрации)
bash scripts/lab5-check.sh --keep       # после проверки оставить приложение запущенным
bash scripts/lab5-check.sh --reset-db   # начать с пустой базы
bash scripts/lab5-check.sh --install    # принудительно переустановить зависимости
bash scripts/lab5-check.sh --no-docker  # PostgreSQL уже запущен, параметры в backend/.env
```
Скрипт создаёт `backend/.env` (если его нет), поднимает PostgreSQL, проходит весь сценарий через HTTP
(регистрация, вход, создание, чтение, изменение и удаление собраний и задач, права доступа, токены, выход)
с проверкой данных прямо в таблицах PostgreSQL. Код возврата `0` — всё в порядке; логи лежат в `.run/`.
Зависимости ставятся только при первом запуске и при изменении `requirements*.txt` / `package-lock.json`.

### Ручная проверка в браузере
1. Откройте http://localhost:5173, зарегистрируйтесь. Обновите страницу — вы остались в системе.
2. **Создание.** «Новое собрание»: название, дата, пункты повестки → «Сохранить»: откроется протокол.
   Пустая форма показывает подсказки под полями.
3. **Редактирование.** В протоколе «Редактировать»: измените название, добавьте пункт повестки, впишите резюме
   и решение → «Сохранить». Протокол обновится сразу.
4. **Задачи.** «Добавить задачу» → форма; карандашом меняются название, ответственный и дедлайн, списком — статус.
   На экране «Задачи» работают фильтры и поиск.
5. **Удаление.** Корзина у задачи и «Удалить» у собрания спрашивают подтверждение; после удаления собрания
   открывается список, а его задач нет на экране «Задачи».
6. **Данные в PostgreSQL.** Перезагрузите страницу — данные на месте. Таблицы:
   ```bash
   docker compose --env-file backend/.env exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select id, title, owner_id from meetings;" -c "select id, title, status from tasks;"'
   ```
7. **Права.** Выйдите, зарегистрируйте второго пользователя: список пуст, а адрес протокола чужого собрания
   (`/meetings/<id>`) показывает «Нет доступа к этому собранию».
8. **Вход и выход.** «Выйти» возвращает на `/login`; переход на `/tasks` без входа снова ведёт на вход.
9. **Истечение токена.** С `ACCESS_TOKEN_EXPIRE_MINUTES=1` через минуту frontend незаметно обновит токены.

## Известные ограничения MVP
- Аудиофайл при создании собрания не загружается на сервер (сохраняется только имя), ИИ-суммаризация не реализована:
  резюме и решения вводятся вручную в диалоге редактирования.
- Задачу нельзя перенести в другое собрание (меняются только её поля).
- Миграций БД нет: таблицы создаются при старте через `create_all`.

## История изменений интерфейса
Существенные изменения и упрощения по этапам:
- **ЛР №3.** Кнопка «Сохранить» в форме нового собрания заработала: повестка вводится списком пунктов, а не одним
  текстовым полем, чтобы проверять каждый пункт. Статус задачи вместо флага «готово / нет» стал перечислением
  `in_progress | done | postponed` (как в backend). В протоколе и на экране задач появились форма создания задачи,
  смена статуса, фильтры и поиск, выделение просроченных дедлайнов; в таблице задач вместо `#id` — название собрания.
  Во всех экранах добавлены состояния загрузки, ошибки и отсутствия данных.
- **ЛР №4.** Добавлены экраны «Вход» и «Регистрация»; в шапке — имя пользователя и кнопка «Выйти». Данные экранов
  стали приходить из API; имитация сервера и режимы `?demo=` удалены. В карточке собрания количество пунктов
  повестки и решений приходит с сервера.
- **ЛР №5.** В протоколе собрания добавлены кнопки «Редактировать» и «Удалить», у задач — редактирование и удаление,
  в таблице задач — столбец «Действия». Список строк (повестка, решения) вынесен в общий `StringListEditor`.
  Тексты ошибок сервера (`422`, `403`) стали понятными, а для `4xx` убрана бесполезная кнопка «Повторить».
